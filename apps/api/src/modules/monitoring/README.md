# HLT-01 support integration proposal

This candidate proposes additive shared staff support DTOs/operations and optional member-confirmed check-in answers, retaining existing support statuses and payload compatibility. Robert reviews shared contracts, generated clients, route/provider/migration registration and member presentation. Existing roles are reused with explicit support-purpose authorization: members access their own requests; assigned active branch officers read disclosures and respond; active branch administrators see assignment metadata and assign an active same-branch officer with fresh MFA and a reason. Other roles have no default disclosure access. No receiving-owner agreement is inferred.

Monitoring owns request persistence, private disclosures, immutable assignment/action history and the staff queue. Member confirmation binds the exact submitted message/check-in and notice version. Unknown/declined answers are explicit. Public responses are distinct from internal staff notes. Versions and stable command keys protect concurrent changes and uncertain retries; authorization is rechecked before replay. All writes and events commit atomically, with no financial writes.

Use Benedict's public `LoanReads.memberLoans` in the actual member transaction to validate an optional linked loan and capture a dated server-owned position. A saved position describes submission time, not a live officer view. A purpose-authorized fresh staff position remains a receiving-owner extension; officers are not given financial roles to access another reader. A loanless help request remains valid without a position. No monitoring calculator or raw servicing-table reader is introduced.

The existing member form/facade is reused. Structured check-ins are optional and require the same preview and renewed sharing confirmation as the message. Member history exposes only the submitted message and published response, never internal notes/assignment reasons. Staff follow-up is a recorded date/action, not an external notification or an amendment. Material corrections are new confirmed submissions retaining earlier history; no in-place rewriting of shared evidence is supplied.

The first slice has no AI dependency, risk score, payment pause, balance change, loan amendment or automatic lending consequence. Review privacy/retention and actual operator assignments before institutional release. Full check, real database/HTTP/browser authorization, retry/rollback tests and actual screenshots are required before integration is claimed.

## Supplied runtime candidate

`MonitoringService` implements the existing member support ports with server-owned member/branch identity and current notice confirmation. It preserves the shared `submitted` → `assigned` → `reviewed` meanings. Optional structured answers include explicit `declined` and `unavailable`; no text inference or mapping from silence to `no` is performed. Members can inspect the exact shared answers and linked loan in their history. Corrections currently require a new confirmed submission; existing disclosures are immutable.

Migrations `001-support.sql`, `002-member-check-in-history.sql` and `003-disclosure-lock.sql` install module tables, forced RLS, explicit safe staff/member views and bounded write/locking functions. Runtime roles have no raw disclosure/action read or direct write privileges. Administrator metadata access excludes messages/notes; staff details require current assignment. Reads hold the request assignment through the transaction, and responding locks it before authorization/replay. The owner function acquires row locks without granting runtime UPDATE. Shared idempotency caches retain only metadata/version receipts; private response snapshots are reconstructed from immutable module history under current authorization. Member events, metadata-only outbox and staff audit/actions commit with the corresponding command.

`/#/member/help` now submits to the actual domain service and offers optional check-in answers and an owned posted-loan selection. The existing preview/edit/renewed-sharing flow and stable uncertain retry are retained. `/#/staff/support-requests` provides scoped metadata paging, a filter explicitly limited to loaded requests, assignment, private disclosures, a response/internal-note distinction, follow-up dates and preserved action history. Assignment requires fresh MFA. A reviewed request means a staff response exists; it is not a resolution or loan amendment. Queue draft discard reloads the current version; ambiguous writes retain the exact request/key. Access denial hides cached disclosures.

The startup adapter uses the public servicing member-loan projection in the member transaction, also supplying the portal's previously unavailable loan read. This is a read integration, not activation of financial-command routes or fictional producers. The saved loan position is from submission time; a fresh support-authorized staff position still needs Benedict's receiving-owner extension. Loanless requests remain usable. The standalone proposed `/health-reviews` operation is still contract-only; the implemented check-ins are explicitly member-confirmed support disclosures. The monitoring capability remains a partial candidate rather than claiming complete health/longitudinal operations.

The existing registration discovers the new migrations through `npm run db:migrate`. Use normal API/web startup, a linked member, an active branch administrator and assigned officer. No permission assignments are seeded by production startup. Existing contributor checks and the [owner brief](../../../../../docs/tasks/production/04-accounting-monitoring.md) contain verification and receiving-owner evidence. Full member history and each request action history currently fail explicitly beyond 100 records rather than silently reporting a complete truncated history; broader pagination is retained work.
