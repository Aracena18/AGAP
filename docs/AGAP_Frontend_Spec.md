### Staff response-history pagination — 4 November 2026

A cursor identifies an immutable action within the same authorized request. Descending versions and an exclusive older-than boundary keep already-open history stable during new appends.

The Response history section shows the loaded count and **Load older responses**. Old receipt projections stay replayable after later history exceeds the legacy limit. A command key used across legacy/paged operations conflicts instead of producing a second action. After a successful response/replay, a separate authorized read refreshes current details without turning a read failure into an uncertain write. Shared generated clients/OpenAPI are updated together. ### Staff follow-up tasks — 4 November 2026

The staff support page has guarded **Support requests** and **Follow-ups** views. Every immutable response with a follow-up date creates a separate staff task atomically; undated responses create none. Migration retains each historical dated action as an open task with no recorded completion evidence. A later dated or undated response does not cancel an existing task. Tasks are private to the current assigned officer; administrators retain assignment metadata only, and member history receives no task notes or completion/reschedule reasons.

Follow-up filters apply across the server queue before bounded UUID paging: all open, scheduled, due today, overdue and completed. Dates are evaluated against an explicit server-provided Asia/Manila calendar date. Stable task-ID ordering avoids moving page boundaries when dates change; this is a live queue, so refresh retrieves changed/new records. Task detail shows the immutable source response, original date, current date/status and bounded newest-first transition history. Older event pages use an exclusive immutable version boundary.

Completion requires a private action-taken note; rescheduling requires a private reason and a different date today or later. Both use task-specific versions, current assignment checks, disclosure locks, CSRF and exact same-key retries. Completed tasks are terminal; further work needs a new dated staff response. Completion records that the staff follow-up was performed, not that the member's concern was resolved. Task transitions leave the original support response, request version, member history and financial records unchanged. Shared caches retain only version receipts; immutable task events reconstruct the original result after later transitions. Date validation happens only during first execution, retaining replay across calendar changes.

Unsaved or uncertain actions prevent switching views/filter/selection. Failed history reads preserve the draft and retry the same cursor. Aborted/disposed reads cannot append old disclosures; later access denial unmounts the private workspace. A confirmed save refreshes the queue separately from write certainty. Existing DTOs/routes remain compatible; additive follow-up schemas/client/controller operations and migration `004-follow-ups.sql` implement this slice. The member-history paging candidate follows below; fresh staff loan positions, external notifications and broader health/receiving-owner acceptance remain pending.

## Architecture and contracts

React + TypeScript + Vite, React Router hash routes, Context/reducer, CSS Modules and shared tokens.
For fictional review routes: one lockfile and one shared CaseRecord. Review feature components receive `record: CaseRecord` and use `useWorkspace()` to access `actor`, `role`, and `saveCase(record)`.
Canonical contracts: `src/domain/types.ts`.

- `assessCase(record): AssessmentResult` — complete/incomplete discriminated result.
- `validateEvidence(record): EvidenceIssue[]` — pure shared evidence-input validation; `EvidenceIssue` is `{ factId, message }` in `src/domain/evidence.ts`.
- `applyCorrection(record, input, actor, at): CaseRecord` — evidence validation and immutable correction.
- `makeRecommendation(record, offerId, note, actor, at): CaseRecord`.
- `validateDecision(record, input): DecisionValidation`.
- `recordDecision(record, input, actor, at): CaseRecord` — snapshot, template, reviewer enforcement.
- `recordFollowUp(record, reviewDate, note, actor, at): CaseRecord`.
- `buildExplanation(snapshot): ExplanationDraft`.

`CaseRepository` exposes list/load/save/reset asynchronously. Browser storage is versioned, structurally validated, and falls back to a visible memory-only mode on failure. Do not erase incompatible persisted data automatically.
Domain modules do not import React, browser storage or feature components. Screens never calculate authoritative money figures.

Calendar rules: explicit first cycle 2026-11-01 through 2026-11-30; group movements by calendar date and calculate end-of-day balances. No intraday or future-cycle guarantee.
Monthly remaining excludes opening cash and purchase-reserved proceeds. Already-deducted obligations appear in evidence but do not reduce take-home pay twice.
Offer total repayment is sum of all scheduled payments; financing cost is repayment + separately paid fees − net received. Fees withheld from proceeds are already reflected in net received.
Evidence readiness and the single assessment engine in `packages/finance/src/assessment.ts` use the same validator for every included cash-flow fact and its referenced source, regardless of `critical`. Referenced sources must be unique, readable and correctly dated; document-supported values require a document/worksheet, and member-reported values require a statement. Unused sources do not block readiness. Readiness excludes offer/cost/policy checks and does not establish authenticity. `src/domain/assessment.ts` remains a compatibility re-export. Fresh assessments use `cash-flow-v2`; historical decision snapshots retain their stored calculation versions and figures.
Demo policies: nonnegative monthly remaining (`monthly-capacity`) and nonnegative daily cash balance (`cash-timing`). Available offers remain explicit; failed policy checks require reviewer exceptions for an approval. Critical evidence gaps cannot be overridden into a complete assessment.
Evidence changes and recommendation changes increase case version. A recommendation carries its resulting case version. Decisions preserve their referenced version; recording a decision and recording follow-up notes do not revise its evidence.
Recommendation and evidence editing are officer actions. Final decisions are reviewer actions. These browser checks demonstrate workflow, not security.
