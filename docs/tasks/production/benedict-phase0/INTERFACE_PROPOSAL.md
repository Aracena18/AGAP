## Proposed in-transaction review-basis handshake

These are responsibilities, not newly registered methods or a prescribed transport between modules:

1. The existing coordinator establishes the real actor and transaction; application/evidence/credit owners return only authorized data within that scope.
2. Application owner checks/locks the command's expected aggregate version and identifies current assessment-input/assignment/workflow bindings. Credit/evidence owners supply a checked immutable assessment/offer/source/fact packet and assert its relationship to current inputs under the same transaction protocol.
3. Benedict constructs the reviewed local context from those projections, never from browser-supplied context JSON. Conflicts/authority come from the agreed approved source, not Qwen or a declaration invented by the caller.
4. Decision rules validate the packet and explicit human request. Revalidate all affected source/product/policy/input bindings at the concurrency boundary before commit; an outbox event that arrives later cannot alone prevent a stale decision race.
5. Persist recommendation/decision/document/acceptance references and owner-controlled status/revision changes, idempotency result, audit and outbox atomically. The caller neither writes another module's table nor opens a nested independent connection.

The current unit of work is not proof that independently read source tables cannot change. Robert/Aaron/Benedict must agree the actual guard/lock protocol, including a stable lock order across application/evidence/credit changes. Phase 0 deliberately does not register a second coordinator or claim an isolation level implements the invariant by itself.

## HTTP and command behavior to preserve

- Reuse the current command bodies and canonical generated transport wherever sufficient. All actors, computed figures, accepted facts, verified status and authority are server-sourced.
- Existing versioned commands require quoted `If-Match`; 428 means missing precondition and 412 stale aggregate version. A different body under an existing idempotency key is 409. Repeat the exact original request/sender/key after uncertainty.
- Phase 1 `DecisionRuleError` is not an HTTP response. Proposed adapter mapping: role/scope/authority denial follows the platform's non-disclosing authorization policy; stale aggregate maps to existing 412; stale assessment/recommendation/material basis is a recoverable workflow conflict; malformed request uses existing validated field-error handling. Robert must agree exact public codes/statuses before registration.
- New update/authorization/confirmation commands need explicit version-resource and idempotency declarations; do not infer them from `POST`. No arbitrary next-state, manual settlement flag or balance patch is accepted.
- Keep known unimplemented operations as 501 `module_not_available` or explicit unavailable views. A generated method/facade implementation does not mean the downstream service exists. Do not mark capability flags available merely because a proposal is accepted.
- Domain services use supplied staff/member transaction contexts. A member-acceptance transaction grants no ledger/payment authority. Notifications use atomic outbox records; irreversible provider calls use durable commands/inbox/recovery rather than blind database-job retries.
