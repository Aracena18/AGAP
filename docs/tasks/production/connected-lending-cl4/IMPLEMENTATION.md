## Selected transport, persistence and UI

1. Canonically adopt the existing safe posted-result, command summary and staff loan-position/workspace schemas with compatibility aliases. Add safe pending-origin details (accepted principal/currency/schedule/application ID, never private authority/acceptance/source packets) needed to prepare the first release. Add scoped, cursor-paged lending applications/loan navigation for cashier, financial authorizer and auditor; label acceptance as a recorded fact, not a claim that current release guards passed. No global priority ranking is implied.
2. Register actual safe workspace, release preparation, separate authorization, submission intent, fictional settlement/status check and finalization endpoints. Every command authenticates actual actor/resource, validates original version/key/body and strict public DTOs, then rechecks authoritative current guards in existing services. A URL loan/command mismatch fails before replay. Return command receipts or safe posted results only. The client never supplies an authority packet, actor, provider key, observation identity, verification Boolean or posted amount.
3. Reuse the actual guarded ServicingService, MoneyService, LendingMoneyProducers, LoanReads and transaction-aware AccountingService. Keep principal-only/simulation configuration and the default-off non-production fictional gate. Distinct preparer/authorizer and actual fresh MFA remain required. Maintain the organization fence and accounting-period-before-application/loan financial lock order.
4. Add a durable server-owned fictional movement inbox keyed permanently to submitted command/provider/business identities, with immutable observation revisions and checksum integrity. Commit the original submission intent before creating fictional settlement. Commit generated movement evidence before domain observation/finalization; a failure or restart cannot erase it or generate another movement under a different key. This is a SQL-backed fictional adapter, not the test-only in-memory driver or proof of actual cash/bank movement. Unknown status stays attached to the original identity; status/reconciliation cannot cause a replacement submission. Server-selected deterministic scenario injection is test-only, never an HTTP verified/outcome authority packet.
5. Persist financial action reasons through append-only scoped notes on the same domain transaction as the changed command/posting. Preserve historical command/snapshot hashes; optional reason metadata is included in new request idempotency only when supplied. Committed retries do not duplicate notes or invent a later reason for an earlier action.
6. Connect normal staff lending navigation, pending-origination preparation and the existing StaffLoanPage through the generated client. Show pending versus confirmed-unposted versus actually posted states accurately, and use the release-specific authorization label. Preserve exact uncertain attempts and refresh current state separately. Repayment transport remains CL5; unsupported actions remain explicitly unavailable until then.
