# Azure and Vercel deployment preparation

This guide prepares the institutional hosting design in the [architecture](../../docs/AGAP_Production_Architecture.md). The separate [credit-only fictional pilot](pilot/README.md) has its own bounded configuration and eligibility/cost guards. [Recorded verification](../../docs/AGAP_Verification.md) establishes no provisioned pilot or live institutional release. Obtain current costs, quota/offer eligibility, and an approved budget before provisioning. Kubernetes is excluded.

## Build and configure

1. Build `docker build -f infra/Dockerfile.api --target api -t agap-api:<git-sha> .` and repeat with target `worker`. Pin the built image digests and scan them before deployment; retain the prior image digest for rollback. Builds include the generated contract check, never model weights or `.env` secrets.
2. After budget approval and renewed Azure sign-in, validate student-offer eligibility, remaining credits, PostgreSQL 18/SKU availability and actual CPU/GPU quotas in the selected region. Public prices do not establish quota. Record the chosen environment, network and SKUs before creating resources.
3. Create separate staging/production resource groups, private PostgreSQL 18 servers/databases and constrained login roles, private Blob containers, identity realms/clients, Key Vault secrets, managed identities and backup destinations. Production/staging must not share session signing keys, OIDC secrets, DB passwords, model tokens or document data. Do not expose PostgreSQL, scanner or GPU ingress publicly.
4. Container Apps: API listens on 4100 with `API_HOST=0.0.0.0`; worker has no ingress and must keep one replica while its polling loop is used. Run ClamAV internally with maintained signatures (48-hour maximum age), at least 3 GiB memory initially; measure before reducing. Give OCR a bounded CPU/memory allocation and private temporary filesystem. Neither OCR nor scanning runs inside API DB transactions. Configure revision health probes and resource limits. Apply least-privilege egress, VNet/private endpoint DNS and TLS.
5. Keycloak runs with HTTPS, an explicit external hostname, database-backed persistent state, production realm/client configuration and a separate database user. Do not deploy `start-dev` or embed development realm secrets. Staff MFA remains mandatory outside the guarded localhost preview. Back up identity data and signing material with the corresponding application/files/key state.
6. Run migrations with a separate operator account, then provision constrained runtime/identity/worker login roles using reviewed grants. API refuses superuser, BYPASSRLS and inherited table-owner credentials. The worker requires membership in `agap_worker`; never give it the owner login. Publish only checksum-reviewed policy files with `npm run policy:publish -- file sha256 organization-id`; no default institutional policy is seeded.
7. Use managed identity for `AZURE_BLOB_ACCOUNT_URL` / `AZURE_BLOB_CONTAINER`; grant the API/worker only the needed container scope. Require container public access disabled, storage public blob access disabled, private endpoints and versioning/backup settings approved by the institution. No SAS is exposed to browsers. Azure secrets are injected from Key Vault into the API/worker, never into Vite configuration.
8. Set `NODE_ENV=production`, exact `PUBLIC_ORIGIN`, OIDC HTTPS settings and `sslmode=verify-full` DB URLs. Staging uses an explicitly labeled staging privacy notice and `EVIDENCE_RECORD_MODE=fictional`; production real mode additionally requires the checksum-bound institutional release record. `EVIDENCE_WORKFLOW_ENABLED` defaults false. Model configuration is optional: absence gives the visible manual-entry flow.
9. Build the pinned baseline GPU environment from the existing [environment versions](../../models/qwen/environment_versions.json); run [the private service](../../models/qwen/service/README.md) on authenticated private HTTPS ingress. Do not enable Experiment D. Provider GPU region/quota, startup time, driver/library compatibility and actual inference need verification before deployment.
10. After the environment API hostname is known, run `node infra/azure/prepare-vercel.mjs HOST` in the deployment checkout to generate `vercel.json`; it refuses to overwrite an existing file. Configure the corresponding Vercel environment, origin and exact Keycloak callback URI. Deploy only after approved hosting eligibility and budget. The external rewrite forwards `/api/*` without a Vercel function; verify full 10 MiB upload/download forwarding, `Set-Cookie`, Origin, CSRF and no-cache behavior. A function proxy has a smaller payload ceiling and must not replace the external rewrite.

## Before traffic / rollback

### Login proxy configuration

Keep `LOGIN_TRUSTED_PROXY_CIDRS` empty until the actual request path is established. For Vercel → Azure ingress → API, record which gateways authenticate the forwarding path and overwrite/append headers, and whether the API hostname is reachable through another route. An IP list alone is insufficient where a gateway/address is shared with untrusted tenants. Verify gateway provenance or isolate/authenticate the route; do not copy a generic private-network range or fixed hop count. Global Express proxy trust stays disabled; the explicit allowlist affects only login limiting, not Host/protocol, redirects or cookies.

Supply at most 32 comma-separated gateway IPs or nonzero IPv4/IPv6 CIDRs. The limiter walks `X-Forwarded-For` from the trusted socket peer right to left, stopping at the first untrusted hop; missing, malformed or all-gateway chains return 503. Untrusted direct peers' forwarding headers are ignored. `LOGIN_RATE_LIMIT_MAX=120` and `LOGIN_RATE_LIMIT_WINDOW_SECONDS=300` preserve the current shared staff/member fixed window. All API replicas must share these values and the session secret. Select actual limits after observing legitimate office/mobile/NAT traffic; network identity does not establish a unique person. 429 includes the remaining `Retry-After`. Keycloak password-attempt and recovery rules remain separately required.

Before enabling trust, demonstrate in staging: distinct clients behind each real gateway, same-client enforcement across replicas/audiences, IPv4/IPv6 normalization, forged/multiple headers, omitted/malformed headers, direct/alternate API access, window recovery and unchanged signed sign-in/MFA/callback/session/CSRF behavior. Local protocol/HTTP tests do not establish this deployment evidence. No gateway list is enabled by this source change.

Apply the complete migration batch before starting a new API revision: decision migration `010-policy-selection.sql` references the selector installed later in that batch by evidence migration `009-policy-selection.sql`; pilot migration `002-policy-selection.sql` then updates its guard. Keep traffic and workers quiesced during migration/cutover. All previous migration bytes/checksums remain unchanged.

Use fictional records for an actual deployed sign-in, member/staff cross-access denial, revoked-session check, 10 MiB file forwarding, unavailable-scanner test, OCR/model failure fallback, lost response replay, worker termination/lease recovery and persistence across restart. Record evidence and responsible-user acceptance. No real records until all gates pass.

Take and restore a consistent PostgreSQL + Blob + Keycloak + key/secret backup into an isolated environment; verify hashes, historical assessments and sign-in after restoration. Approve retention, legal holds, deletion/erasure procedure, RPO/RTO and offsite recovery before real mode. The source/assessment metadata history remains immutable; file deletion requires a separately approved retention decision. No automatic retention duration is invented here.

Roll back API/worker to the retained image digest and disable new writes if a migration or financial output fails. Do not downgrade or mutate saved assessments; keep the additive schema and inspect compatibility before resuming an older binary. Quiesce workers and traffic before a full recovery. Restore the complete consistent snapshot into a separate environment, reconcile counts/hashes and use an approved cutover. Never restore only the application DB while leaving incompatible identity/files state.

## Retention execution

`npm run evidence:retire -- manifest.json sha256 plan` checks an operator-supplied, checksum-bound per-source decision; `execute` performs it only after the specified date and with no active hold or worker lease. The manifest requires organization/source IDs, actual policy/approval/operator references, a worker-quiescence reference and `deleteNotBefore`. Quiesce the relevant workers and confirm all external I/O has stopped before execution; do not invent the institutional retention period. Active holds are maintained only by authorized operators, locking the same source row before changing a hold.

Execution first records a durable retirement and denies downloads/source confirmation, then removes original and all reserved derived-text objects outside database transactions and records completion. Rerun the identical manifest after an interrupted deletion. A different decision cannot silently replace it. This is file-content retirement; immutable financial facts, approved audit history and saved assessment snapshots follow their separately approved financial-record retention requirements. It does not claim to implement whole-member erasure. Reconcile and remove abandoned upload-intent/temporary objects only under an approved operator cleanup decision; they are never published as cleared sources.
